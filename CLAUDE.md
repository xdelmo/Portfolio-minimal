# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

- Node 24 (from `.nvmrc`; Angular 22 needs ≥ 24.15) lives in `~/.local/node/current` on both machines; the `SessionStart` hook in `.claude/settings.json` puts it on the PATH, so commands need no prefix (run each one from the worktree, never `cd` into the main checkout)
- `npm start` — both dev servers: open http://localhost:4200 (English under `/en/`, Italian under `/it/` proxied from port 4201, so the language switch works); `npm run start:it` runs only the Italian one
- `npm run verify` — the CI gate locally (lint, unit, scripts, build, e2e), stops at the first failure. Run it before saying a task is done and judge it by its exit code, never by grepping the output (a grep once hid 3 lint errors). WebKit runs through `npm run e2e:webkit` (below). The e2e start their own server on port 4300 and stop if the port is taken (`reuseExistingServer: false`, issue #218): stop the other server (`lsof -ti :4300`), often another worktree's run
- Two machines: a fanless MacBook Air and a 4-core Linux PC (ThinkCentre M710q). On both: while iterating run only the affected test (one spec file, `--project=chromium`), keep the full `npm run verify` for the end, and never run two suites or builds at once (check `pgrep -fl "playwright|ng build|vitest"` first)
- `npm run build` — static prerender of both locales into `dist/portfolio/browser/{en,it}` + sitemap/robots; never `ng build --localize=en` for a quick check: it writes a layout without `en/` and the e2e server stops working
- `npm run lint` — ESLint strict (typescript-eslint strictTypeChecked + angular-eslint, template a11y), zero warnings allowed
- `npx ng test --no-watch` — unit tests (Vitest); one file: `npx ng test --no-watch --include src/app/core/theme/theme.spec.ts`
- `npm run e2e` — Playwright against the built site (run `npm run build` first); one test: `npx playwright test e2e/theme.spec.ts --project=chromium`
- `npm run lhci` — Lighthouse CI against the built site (mobile, performance ≥ 0.95, best of 3 runs). On the Linux PC `scripts/lhci.sh` runs it with Playwright's Chromium and no sandbox. It serves `dist` statically, so `lighthouserc.json` lists case studies with a trailing slash (the slash-less URL would cost a redirect Netlify does not make)
- `npm run i18n:extract` — regenerate `src/locale/messages.xlf` (git-ignored, generated) after changing template strings, then add the units by hand to `messages.it.xlf` (the only tracked one)
- `npm run verify:deploy -- <url>` — checks redirects, 404s and the SEO/GEO files on a Netlify deploy (preview or production)
- `npm run test:scripts` — tests for the build scripts (`node --test scripts/*.test.mjs`)
- `npm run verify:quick` — lint, unit and script tests in about a minute (no build, no e2e): the check while iterating, `verify` stays the gate. TestBeds for pages and sections take `testProviders()` from `src/testing/test-providers.ts`
- Handbook (issue #454): public MkDocs Material site in Italian, pages in `handbook/`, nav in `mkdocs.yml`, published on GitHub Pages from `master` by `.github/workflows/docs.yml`. Build it with `python3 -m venv .venv && .venv/bin/pip install -r handbook/requirements.txt`, then `.venv/bin/mkdocs serve` or `build --strict`. It is public: no secrets, hook URLs, e-mail addresses, local paths, private repo names, nor content from `docs/launch/`, `docs/superpowers/` or `.claude/`; `node scripts/handbook-check.mjs` stops on the first four and its test runs in `test:scripts`. Its look follows the site (`handbook/stylesheets/extra.css`, the site's own font file, the moai in `handbook/.overrides/.icons/`)

## Git workflow

- Every problem the user reports gets a GitHub issue first (`gh issue create`), before any investigation or fix; its branch carries the number (`fix/<n>-topic`) so `triage.yml` links the pull request to it (the user's rule, 2026-10-08).
- Every change gets its own branch off `origin/devel` (`git fetch` first; `master` lags `devel` until a release), named `<prefix>/<topic>` so the user can tell what a merge was from its name: `feat/` (new things), `fix/`, `docs/`, `chore/`, `ci/`, `test/`, `refactor/`, `perf/`, `style/`, `build/`; never a direct commit on `devel` or `master`. `scripts/branch-name.mjs` enforces it in the `pre-push` hook and in CI, so rename a branch before pushing (worktree tools name theirs `worktree-…`). New issues and pull requests are assigned, labelled and linked by `.github/workflows/triage.yml`.
- Before pushing, run the specs and unit tests the change touches (seconds, not the 20 minutes of `verify`); then `npm run ship -- --title "…" --body-file <file>` (`scripts/ship.sh`, run it in the background and wait for its notification, never poll): it pushes, opens the PR into `devel`, waits for the Actions checks and merges with `--rebase --delete-branch` only when they pass (the user does not review PRs; the repository allows rebase and merge commits only, squash is disabled). A red CI is fixed on the branch first, never merged; a docs-only PR waits for its CI too.
- CI on the pull request is the full gate (the pokèverba flow, issue #223): the `pre-push` hook in `.githooks/` (enabled by `npm install` through `prepare`) only checks branch names and refuses direct pushes to `devel` and `master` (`scripts/branch-name.mjs`; the owner's escape hatch is `ALLOW_PROTECTED_PUSH=1 git push …`). Never bypass it with `--no-verify`. `npm run verify` still runs the whole CI locally when a change is risky (motion, timing, WebKit); on the Mac wrap it in `caffeinate -is`, or a fanless Mac left alone sleeps half way through (issue #214).
- WebKit and iPhone do not run natively on the Mac (macOS 14): `npm run e2e:webkit` (part of `verify`) runs them in CI's Linux Playwright image through OrbStack, about 5 minutes; extra arguments go to Playwright (`npm run e2e:webkit -- e2e/moai.spec.ts`). On the Linux PC (Ubuntu 26.04, which Playwright's WebKit does not support: it launches but canvas animations never advance) `npm run e2e:webkit` runs them in the same image through Docker, about 10 minutes. There git has no global identity: the repo's local `user.name`/`user.email` are set to the user's. Most red CI runs before it were WebKit/iPhone failures nobody had seen locally. For a CI failure anyway, `gh run download <run-id>` gets the failed run's `test-results` (under `reports-*`); a test with a `-retry1` folder failed twice, one without it passed on retry. Read the steps and their durations from `trace.zip` before changing anything, and fix the cause rather than rerunning until green.
- A CI failure that says "The job was not acquired by Runner" is GitHub's runners, not the code: `gh run rerun <id>`; it still is not a green CI.
- A pull request that shows only Netlify's checks has started no Actions workflow (seen 2026-11-08: opening a PR, reopening it and merge pushes started nothing for hours, while issue events still ran Triage): `gh api "repos/xdelmo/Portfolio-minimal/actions/runs?head_sha=<sha>"` counts its runs; a new non-empty commit on the head branch starts them (`pull_request` synchronize). An empty one is dropped by the rebase merge, and never merge without the CI.
- `devel` collects the work; when it is ready, one large pull request `devel` → `master` takes it live, merged with a merge commit (not squash, to keep `devel`'s history), and only after the user's explicit yes. Issues fixed on `devel` close when that pull request merges (`master` is the default branch); close by hand any it does not. `v2` is retired (live on 2026-10-25, PR #267): no new branches off it or pull requests into it.
- When several branches wait to be shipped, push first the ones that improve the automation (hooks, CI, scripts, guards), then features and content: every later push benefits from them (the user's rule, 2026-10-07).
- The `pre-commit` hook runs ESLint on the staged files, so a lint error stops the commit, not the push.
- Locally `verify` stops the e2e at the first failure (`--max-failures=1`); CI runs them all for the full report, then repeats the specs the pull request changes 5 times (`e2e:changed`).

## Lessons from failures

Read `CODING_STANDARDS.md` before writing tests or motion code and when reviewing a diff: every failure that reached CI and could not get an automatic guard left a rule there.

## Architecture

Angular 22 (standalone, zoneless, signals), fully prerendered (`outputMode: "static"`, no Node server), deployed on Netlify. Spec: `docs/superpowers/specs/2026-10-03-portfolio-v2-design.md`; plans in `docs/superpowers/plans/` (each opens with its status); every change to the spec gets a row in its §17 (`.gitattributes` merges the spec with `union`, so rows appended by parallel branches never conflict on a local rebase; GitHub's server merge ignores it, so a PR that conflicts after another one merged gets `git rebase origin/devel` locally, then `git push --force-with-lease`, then its CI again). Manual launch steps, open questions for the user and the cleanup only they can do: `docs/launch/launch-kit.md`.

- Two locale builds via `@angular/localize`: English is the template source language, Italian lives in `src/locale/messages.it.xlf` (missing translations fail the build). UI strings use explicit `@@ids`; long content comes from `src/app/content/content.{en,it}.ts`, picked by `LOCALE_ID` through the `CONTENT` token.
- Logic that can break lives in pure, unit-tested functions next to thin services: `core/theme/theme.ts`, `core/i18n/locale.ts`, `core/seo/seo.ts`.
- Theme: an inline script in `src/index.html` sets `data-theme` before first paint; `ThemeService` takes over after hydration. All colors are CSS variables in `src/styles/_tokens.scss`.
- Netlify (`netlify.toml`) does the language redirect on `/` (honouring the `nf_lang` cookie set by the language switch), the canonical-domain 301s, legacy Gatsby URLs and per-locale 404s. `scripts/postbuild.mjs` also writes `_redirects` (200 rewrites so case studies answer at their slash-less canonical URL). The Netlify UI must not have `@netlify/plugin-gatsby` installed: it fails every Angular deploy.
- Motion: GSAP (ScrollTrigger, SplitText) loads as a lazy chunk through `MOTION_LOADER`; the `[appMotion]` directive (`src/app/motion/motion-host.ts`) runs the effects in `src/app/motion/effects/` inside `gsap.matchMedia`, and does nothing with reduced motion. Pins and pointer effects are desktop only (≥ 1024px with hover). Use `gsap.set` + `.to()` for scrubbed tweens (a scrubbed `.from()` is not redrawn in Firefox after a refresh). E2E skip the intro through `e2e/fixtures.ts`. `MotionHost` starts each effect in its own task and `motion/gsap.ts` evaluates GSAP, ScrollTrigger and SplitText one import at a time: all at once they were long tasks that kept the home at 0.93 on Lighthouse (TBT). Do not wrap home sections in `@defer (hydrate …)`: the pins and the thread measure them before they hydrate (tried 2026-10-08, five e2e failed). Smooth scroll is GSAP's ScrollSmoother (`motion/smoother.ts`, started in `motion/gsap.ts` before any effect, issue #159): desktop with a mouse only, never with reduced motion; it moves `#smooth-content` with a transform, so fixed things and the header live outside `#smooth-wrapper` (the header turns `fixed` under `html.smooth`), `position: sticky` inside is replaced by `effects/sticky.ts` (put `data-sticky` on the element), and scrolling from code goes through `smoother()` (anchors and page changes in `app.config.ts`). The e2e turn it off (`e2e/fixtures.ts`, `smoothScroll`); a test about it opts in and waits for the content to rest with the lag-smoothing bound of `e2e/smooth-scroll.spec.ts`. `MotionPause` (`src/app/motion/pause.ts`) is the one pause switch: Angular code injects it, GSAP effects use `watchPause()`. Effects that move elements GSAP also transforms go through CSS `translate` variables. `PixelDissolve` (`src/app/pixel-dissolve/`) draws the band seams; `effects/dissolve.ts` scrubs its `--p` (seams form as they scroll in and crumble as they rise to the header), `effects/thread.ts` drives the home's pixel thread.
- First paint: the LCP is the hero headline (text), and Lighthouse puts every request started before the first paint on its critical path. So `MOTION_LOADER` imports GSAP only `afterPaint()`, project images are never `priority` (the hero fills the first screen) `index.preloadInitial` is off, and `scripts/after-paint.mjs` (in postbuild) swaps Angular's module scripts and modulepreloads for one inline loader that starts them after the first frame (issue #151: FCP 1.9 → 1.2 s on Lighthouse); Three.js (moai) and the player card are lazy chunks too.
- Easter egg: `src/app/game/game-trigger.ts` (app shell) opens the lazy player card on the Konami code, five taps on the logo, or a click on any `[data-press-start]` (the footer key, rendered only after hydration).
- Links to GitHub repositories: the content files keep every repository URL; `scripts/public-repos.mjs` (run before build, start, verify and on `npm install`) asks GitHub which ones a visitor can open and writes the git-ignored `src/app/content/public-repos.generated.ts`; `onlyPublic()` drops the others from `CONTENT` and from `llms.txt`/Markdown, and the build publishes the list as `/repos.json`. `.github/workflows/repos.yml` compares it with GitHub every day and starts a Netlify build through the `NETLIFY_BUILD_HOOK` secret when it changes. Never hard-code which repositories are public (issues #80, #81).
- Security headers: `scripts/postbuild.mjs` writes `_headers` with a Content-Security-Policy built by `scripts/security-headers.mjs` from the prerendered pages (the site's own scripts plus the hashes of the inline ones, recomputed at every build) and the other headers (nosniff, no framing, referrer, permissions). Anything loaded from another origin needs its source added there; `e2e/csp.spec.ts` serves the pages with the policy and fails on any violation, `verify:deploy` checks the headers on a deploy (issue #113).
- Blog (issue #1, spec `docs/superpowers/specs/2026-10-11-blog-design.md`): every post is `src/app/content/blog/<slug>/{en,it}.md` with flat frontmatter (`title`, `description`, `date`, optional `updated`, `project`, `linkedin`); `scripts/blog.mjs` (inside `npm run generate`, which build, start, verify and `npm install` run) turns them into the git-ignored `src/app/content/blog.generated.ts`, read through the `BLOG` token, and stops the build on a post missing a language or a field. A new post also needs `npm run og:images`.
- `scripts/postbuild.mjs` builds `sitemap.xml` and `robots.txt` at the publish root from the prerendered pages' canonical/hreflang tags; its `_headers` gives each hashed build file a year of `immutable` cache (issue #153).

## Conventions

- Site content is bilingual (English source, Italian translation).
- No green anywhere in the palette (the user's brand colours are greys, the `--accent` blue family, lavender and peach).
- Styles are SCSS (`inlineStyleLanguage: scss`, `includePaths: [src]`); colors stay CSS custom properties because the theme switches them at runtime; use `@use 'styles/breakpoints' as bp;` and `@include bp.up(md)` for breakpoints.
- The whole site must meet WCAG 2.2 AA (spec §11): axe runs with WCAG tags in both themes in the e2e suite.
- Visual style directives live in the project skill `.claude/skills/edm-style/SKILL.md` (palette, type, 8px grid, stepped shapes, the living objects, motion rules): read it before any visual change. `DESIGN.md` carries the same system's tokens and rules in the DESIGN.md format, `PRODUCT.md` the product context, both for the impeccable skill; edm-style and the code win where they differ. The original visual system is in plan 1, section "Sistema visivo".
- The old Gatsby site lives on `master`; its images can be recovered with `git show master:content/images/<file>`.
- Project images live in `public/images/work/` as WebP (about a third of the JPEG, issue #353; re-encode new ones with Chromium's canvas `toDataURL('image/webp', 0.8)`): the original at full width plus a half-width copy named `<name>-<width/2>.webp` (`workImageLoader` builds the `srcset` from them). Set `width`/`height` in both content files to the original size.
- Open Graph images are committed in `public/og/`: run `npm run og:images` after changing a title, a summary or the project list (the build fails if a page points at a missing one). The build also writes `llms.txt` and a Markdown copy of every page from the content files.
- Fonts: `src/styles/_fonts.scss` declares Instrument Sans from `@fontsource-variable` with `font-display: optional`, and `scripts/postbuild.mjs` injects a `<link rel="preload">` for the latin file into every page. Together they keep CLS at 0; do not switch back to the package CSS (it uses `swap`).
